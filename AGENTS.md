# AGENTS.md

## Задача этого файла

Этот файл нужен как **handoff для следующего ИИ/агента**.

Главная практическая цель на следующем этапе:

> сделать в проекте **нормальную поддержку разных размеров картинок для SDXL**,
> не копируя чужую реализацию,
> а доведя до ума уже существующий каркас в этом репозитории.

Важно: цель — не повторить Local Dream один-в-один по внутренностям, а получить **тот же пользовательский результат** через **нашу собственную архитектуру**.

---

## Жёсткие правила

1. **Не копировать код** из `Local Dream`, `stable-diffusion.cpp` и других внешних проектов.
	 - Их можно использовать только как источник идей, архитектурных паттернов и проверок гипотез.
	 - Репозиторий должен оставаться **самостоятельным проектом**.

2. Не пытаться сейчас делать «true arbitrary size из любого WxH на лету».
	 - Для SDXL на QNN практический путь сейчас — это **набор заранее собранных resolution buckets**.
	 - То есть сначала нужен пользовательский эффект “разные размеры работают”, а уже потом — более хитрые схемы упаковки/патчей.

3. **Не использовать встроенный image viewer** редактора/агента для просмотра изображений.
	 - В этой рабочей среде это ломает серверную часть.
	 - Если нужна проверка изображений — только через собственные скрипты/утилиты.

4. Не заявлять новые speed-рекорды без реального прогона на телефоне.
	 - Телефон может быть отключён.
	 - Без телефона можно и нужно готовить архитектуру, сборку, экспорт, deploy path, synthetic tests.

5. Если делаешь изменения под dynamic resolution, не ломай текущий `1024x1024` fast path.
	 - `1024x1024` должен остаться рабочим эталоном и fallback-вариантом.

## Самая важная мысль

### Dynamic resolution у нас уже почти намечен

Не надо начинать с нуля.

В репозитории **уже есть задел** почти на всех уровнях:

- **runtime** уже умеет принимать `--width` / `--height`;
- **runtime** уже умеет искать `context/WxH/...`;
- **runtime** уже умеет снапать запрос к ближайшему доступному размеру;
- **APK UI** уже имеет width/height поля и пресеты;
- **deploy helper** уже умеет рекурсивно пушить `context/**`;
- **host-side export/build** уже знает про несколько разрешений.

То есть главный bottleneck сейчас не в том, что “архитектуры нет”, а в том, что её надо **досшить до конца**.

## Что реально мешает получить «разные размеры как у Local Dream SD»

### Не хватает не runtime-идеи, а завершённого production loop

Нужно довести до конца такие куски:

1. **Стабильный список поддерживаемых resolution buckets**
2. **Экспорт / ONNX / compile / context generation для каждого bucket**
3. **Нормальный layout артефактов по папкам `context/WxH/`**
4. **Динамическое чтение списка доступных размеров в APK**, а не hardcoded пресеты
5. **Проверка end-to-end на телефоне** для нескольких bucket’ов
6. **Честная документация**, что пока это preset buckets, а не магический arbitrary resize

## Самый правильный путь реализации

### Этап 1 — не patch-система, а per-resolution contexts

Не надо сейчас повторять Local Dream patch-механику для SD1.5.

Для этого репозитория намного проще и правильнее сначала довести до рабочего состояния такую схему:

- общий `clip_l.serialized.bin.bin`
- общий `clip_g.serialized.bin.bin`
- per-resolution папки:
	- `1024x1024/`
	- `1216x832/`
	- `832x1216/`
	- `1344x768/`
	- `768x1344/`
	- при необходимости позже `1152x896`, `896x1152`

Внутри каждой папки:

- `unet_encoder_fp16.serialized.bin.bin`
- `unet_decoder_fp16.serialized.bin.bin`
- `vae_decoder.serialized.bin.bin`

Это уже ляжет на существующую логику `phone_generate.py` почти без архитектурного слома.

### Почему это лучше сейчас

Потому что:

- runtime уже поддерживает такой layout;
- deploy script уже поддерживает такой layout;
- APK уже умеет выбирать размеры;
- это даёт быстрый путь к user-facing результату: “разные размеры работают”.

## Что должен сделать следующий ИИ

### Шаг 1. Зафиксировать поддерживаемые SDXL buckets

Не пытаться стартовать с “любое кратное 8”.

Нужно начать с конечного списка, например:

- `1024x1024`
- `1216x832`
- `832x1216`
- `1344x768`
- `768x1344`

Опционально потом:

- `1152x896`
- `896x1152`

Важно:

- брать только такие размеры, которые реально разумны для SDXL-Lightning path;
- не плодить слишком много buckets до первой валидации.

### Шаг 2. Довести host-side export/build path

Нужно проверить и, если надо, допилить:

- `scripts/build_all.py`
- `SDXL/export_sdxl_to_onnx.py`
- `SDXL/debug/make_calibration_data.py`
- `SDXL/debug/quantize_unet.py`
- весь дальнейший QNN compile/context generation path

Цель:

> чтобы один host-side запуск мог собрать артефакты сразу для нескольких resolution buckets.

Желательный результат:

- либо один master script;
- либо отдельный multi-resolution helper, который:
	- принимает список `WxH`
	- экспортирует ONNX для каждого размера
	- компилирует/генерирует нужные context binaries
	- раскладывает всё сразу в `build/.../context/WxH/`

### Шаг 3. Нормализовать layout артефактов

Нужно сделать один канонический layout для dynamic resolution.

Рекомендуемый layout:

```text
<base>/context/
	clip_l.serialized.bin.bin
	clip_g.serialized.bin.bin
	1024x1024/
		unet_encoder_fp16.serialized.bin.bin
		unet_decoder_fp16.serialized.bin.bin
		vae_decoder.serialized.bin.bin
	1216x832/
		unet_encoder_fp16.serialized.bin.bin
		unet_decoder_fp16.serialized.bin.bin
		vae_decoder.serialized.bin.bin
	832x1216/
		...
```

Опционально добавить:

```text
<base>/context/manifest.json
```

Где хранить:

- список реально доступных размеров;
- version/revision;
- maybe checksums/metadata.

### Шаг 4. Сделать APK не hardcoded, а data-driven

Сейчас `MainActivity.java` использует hardcoded `SDXL_SIZE_PRESET_DIMENSIONS`.

Это нужно улучшить так, чтобы APK:

1. делал runtime check;
2. получал список `available_resolutions`;
3. строил spinner/presets из **реально доступных contexts**, а не из зашитого массива;
4. если exact resolution отсутствует — либо:
	 - честно показывает snap target,
	 - либо запрещает запуск exact size,
	 - либо даёт пользователю выбрать только реально доступные buckets.

Рекомендуемая логика:

- в UI показывать **только реально доступные размеры**;
- скрытый snap оставить как fallback для CLI/debug,
- но в APK не делать “тихий подменённый размер” без явного статуса.

### Шаг 5. Довести runtime UX

`phone_generate.py` уже умеет снапать размер к ближайшему доступному.

Нужно решить UX-политику:

- CLI/debug режим: snap можно оставить;
- APK/user режим: лучше или явно показывать snap, или не использовать его автоматически.

Нужен честный лог, например:

- requested: `1152x896`
- actual: `1216x832`

или вообще не давать запускать неподдержанный exact size через APK.

### Шаг 6. Протестировать end-to-end

Когда телефон снова будет подключён, минимум прогнать:

- `1024x1024`
- `1216x832`
- `832x1216`

Проверять:

- runtime не падает;
- размер итоговой картинки правильный;
- preview/vae/latent path не ломаются;
- UNet encoder/decoder действительно берутся из нужной папки `WxH`;
- APK не подсовывает silently другой размер без логов.

### Шаг 7. Только после этого думать про более хитрую упаковку

Если buckets заработают стабильно, только потом можно рассматривать:

- delta-патчи артефактов;
- compressed delivery;
- manifest-driven download on demand;
- Local Dream-like storage optimization.

Но это **не первый шаг**.

## Самое важное инженерное решение

### Не пытаться сделать arbitrary resolution раньше времени

Для этой архитектуры сейчас правильная цель звучит так:

> “не arbitrary size”, а **“набор поддерживаемых и реально собранных SDXL buckets, которые прозрачно выбираются пользователем”**.

Это уже даст то, что пользователь хочет на практике:

- не только `1024x1024`;
- нормальные вертикальные и горизонтальные варианты;
- predictable deploy/runtime path;
- без магии и без копирования чужих решений.

## Definition of Done

Считать задачу реально сделанной только если выполнено всё ниже:

1. На хосте можно собрать **несколько SDXL resolution buckets**.
2. На телефоне они раскладываются в `context/WxH/`.
3. `phone_generate.py --list-resolutions` показывает их корректно.
4. APK предлагает пользователю реальные доступные размеры.
5. Генерация проходит минимум на 3 размерах.
6. Итоговый PNG имеет правильный реальный размер.
7. Документация честно говорит, что это preset buckets, а не arbitrary-size magic.

Если смотришь на Local Dream или похожие проекты, держи в голове:

- нам **не нужно** их копировать;
- проект должен оставаться **нашим собственным**;

- внешние проекты нужны только чтобы понять, какие UX/packaging идеи уже существуют и чего стоит избегать.

Dynamic resolution здесь нужно делать как **свою собственную, понятную и поддерживаемую систему**.

## Короткий practical summary для следующего ИИ

Если совсем коротко:

1. Не трогай базовую split-UNet архитектуру.
2. Не делай patch-систему первой итерацией.
3. Доведи до конца **per-resolution context buckets**.
4. Используй уже существующие хуки в `phone_generate.py`.
5. Сделай APK data-driven по доступным размерам.
6. Проверь `1024x1024`, `1216x832`, `832x1216` end-to-end.

Это самый короткий путь к реальным “разным размерам картинок”.
